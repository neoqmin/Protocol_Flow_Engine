# 위협 모델 · 키 관리 · 라이선스 원칙

초안. MVP-A 시작 전에 리뷰하고 확정한다. 법률 관련 내용은 자문이 아니며 배포 전 법무 검토가 필요하다.

## 1. 보호 대상 (Assets)

- 터널로 전달되는 사용자 트래픽의 **기밀성·무결성**
- 세션 키, 사설키, 인증서 자격
- 엔진의 가용성 (파서/상태머신이 악성 입력으로 죽지 않을 것)
- (Post-MVP) 배포되는 Flow 정의의 무결성

## 2. 공격자 모델

| 공격자 | 능력 | MVP 대응 |
|---|---|---|
| 네트워크 수동 관찰자 | 패킷 캡처 | TLS 1.3 + tls-crypt + AES-GCM |
| 네트워크 능동 공격자 | 패킷 변조/삽입/재생/드롭 | AEAD 검증, replay window, 제어 채널 reliability + tls-crypt HMAC |
| 악성/비정상 peer | 잘못된 형식·거대 메시지·상태 위반 | 엄격한 파서, 길이 상한, 상태머신 검증, fuzzing |
| 로컬 비특권 프로세스 | 메모리/파일/소켓 접근 시도 | 키 파일 권한, 메모리 zeroization, 로그에 비밀 금지 |
| 중간 노드(프록시/Relay, Post-MVP) | 트래픽 관찰/차단/조작 | **신뢰하지 않음**: 종단 간 암호화, Relay는 키를 갖지 않음 |

비목표(Non-goals): 호스트가 완전히 장악된 상황, 하드웨어 사이드채널, 트래픽 분석(길이/타이밍) 방어.

## 3. 신뢰 경계

```text
[네트워크] ──(비신뢰)── [Transport] ── [Parser/Crypto Block] ── [Key Manager] ── [TUN/앱]
                                         ↑ 모든 입력은 여기서 검증      ↑ 비밀은 이 안쪽에만
```

- Transport 이후 첫 Block(파서)부터 모든 입력을 **비신뢰 데이터**로 취급한다.
- 비밀(키)은 Key Manager 안에서만 보관한다. Flow/Block 설정·로그·오류 메시지·테스트 golden에 나타나지 않는다.

## 4. 키 관리

| 항목 | 규칙 |
|---|---|
| Key Reference | Flow/Block은 키 값이 아니라 **불투명 핸들(Key Reference)** 만 다룬다 |
| 저장 | 사설키/인증서: 플랫폼 저장소(Keychain, Android Keystore, Windows DPAPI/CNG, Linux 파일 권한/키링). 세션 키는 메모리만 |
| Zeroization | 세션 키·중간 키 재료는 사용 후 즉시 지운다 (`explicit_bzero`, `SecureZeroMemory` 등 컴파일러가 제거하지 않는 방식). 테스트로 검증 |
| 수명 | 재협상 주기를 강제한다. AEAD packet-id가 고갈(랩어라운드)되기 **전에** 반드시 새 키로 전환하고, 불가능하면 연결을 종료한다 (nonce 재사용 금지) |
| 난수 | OS CSPRNG만 사용 (자체 PRNG 금지) |
| 비교 | MAC/태그 비교는 상수 시간 |
| 노출 금지 | 키는 DSL/Flow JSON/로그/크래시 덤프/테스트 벡터에 평문으로 남기지 않는다. 개인 키 커밋 금지 |
| 암호 라이브러리 | 자체 구현 금지. 검증된 라이브러리(OpenSSL/BoringSSL 등)를 수정 없이 링크 (Provider 인터페이스 뒤에 둔다). 모바일 선택은 PM-1에서 확정 |

## 5. 보안 개발 요구사항

- 모든 파서/디코더에 **fuzz 타깃 또는 전수 테스트**를 둔다 (현재: 헤더 파서 전수 테스트 + libFuzzer 타깃).
- CI에 ASan/UBSan 잡 유지. 새 코드는 `-Werror` 통과.
- 길이/개수 필드는 상한을 두고 정수 오버플로를 검사한다.
- 보안에 영향을 주는 결정(nonce 구성, 재협상 정책)은 `docs/DECISIONS.md`에 기록하고 테스트로 고정한다.
- 서명되지 않은/검증 안 된 Flow를 보안 경로에 로드하지 않는다 (PM-7 이후 상세화).

## 6. 라이선스 / Clean-room 원칙

- 독립 구현(D-006)은 GPL 코드와의 링크 문제를 피할 수 있으나, **OpenVPN 소스를 보고 옮기면 파생 저작물 논란**이 생길 수 있다. 따라서:
  - 구현 근거는 공개 문서·RFC·pcap 관찰로 한정한다 (`docs/OpenVPN_Interop_Profile.md` §5).
  - 소스에서 가져온 코드 조각·구조를 복사하지 않는다. 의심되는 경우 기록하고 리뷰한다.
- **iOS/App Store 배포**: GPL 코드를 앱에 포함하는 것은 배포 약관과 충돌한 전례가 있으므로, iOS 빌드에는 GPL 코드를 포함하지 않는다. 의존성 라이선스를 `third_party/README.md`에 기록하고 CI에서 목록을 점검한다.
- OpenVPN 바이너리/DCO 모듈은 **테스트 상대 또는 별도 프로세스로만** 사용하고 우리 바이너리에 링크하지 않는다.

| 항목 | 방식 |

## 8. Post-MVP 예정 위협 (계획 단계, 해당 마일스톤 진입 시 확정)

근거: `docs/PM2_NAT_Traversal_Scope.md`(PM-2b), `plans/Protocol_Flow_Engine_Flow_Model_Extension_Plan.md`(F-1~F-3).

### 8.1 NAT Traversal (PM-2b)

| 위협 | 대응(안) |
|---|---|
| STUN 응답 위조·주입(잘못된 공인 주소를 믿게 함) — **N3에서 구현(D-047)**: CSPRNG transaction id(`RandomSource`), 보낸 서버 주소에서 온 응답만 수락(탐지 probe 제외), 쓸 수 없는 응답은 버리고 재전송 계속. MESSAGE-INTEGRITY 검증은 자격증명이 생기는 N4/N5에서 | transaction id는 CSPRNG 96비트, 보낸 요청과 출처·id가 일치하는 응답만 수락. 인증 가능한 경우 MESSAGE-INTEGRITY(-SHA256) 검증. 공인 주소는 **힌트일 뿐**이고 연결 신뢰는 항상 VPN 계층의 TLS/AEAD가 결정한다 |
| hole punching probe 위조(제3자가 피어인 척 응답) | connectivity check에 시그널링으로 교환한 비밀(KeyRef)로 만든 인증을 붙인다. 인증되지 않은 probe는 `Drop` |
| 열린 TURN Relay 남용(우리 Relay가 타인 트래픽 중계에 쓰임) | 자격증명 필수, permission은 rendezvous로 확인한 상대 주소에만, 할당 수·수명·대역폭 한도. **D-044로 자체 TURN 서버(연결 서버 `pf_connectd`)를 운영하므로 이 책임은 우리 것이다** — N5 종료 조건에 인증·한도·permission 강제 테스트를 둔다 |
| Relay·시그널링 서버의 트래픽 관찰·조작 | §2의 "중간 노드" 원칙 그대로: **신뢰하지 않음**, 종단 간 암호화, Relay는 키를 갖지 않음. N5 종료 조건에 "Relay 쪽 캡처에 평문 없음"을 둔다 |
| 동의 없는 트래픽 송신(공격 증폭) | ICE consent freshness(RFC 7675)식 주기적 동의 확인. 응답 없는 대상에는 송신 중단. probe 속도 상한 |
| UPnP/NAT-PMP/PCP로 사용자 공유기 포트 개방 | 기본 비활성, 명시적 사용자 동의, 매핑 수명 최소·종료 시 해제, 개방 내역을 로그에 남김. D-004의 "사용자 관리 네트워크" 전제 |
| TURN/STUN 자격증명 노출 | Key Reference로만 다룬다. Flow·시나리오 JSON·trace·로그에 평문 금지(Flow JSON v1 `SecretLiteral` 규칙을 시나리오 형식에도 적용) |
| 시뮬레이터·랩의 악성 입력 | STUN/TURN 코덱은 fuzz 타깃 필수, 속성 개수·길이 상한 |
| rendezvous 남용(등록 위조, 서버 목록 수집, 남의 서버로 연결 유도) | 등록·조회 모두 자격증명 필요(KeyRef), 조회 권한(어떤 클라이언트가 어떤 서버를 찾을 수 있는가), 속도 한도. 최종 신뢰는 항상 VPN 계층의 TLS 인증서 검증이 결정한다(잘못된 후보로 유도돼도 인증 실패) |
| 연결 서버 장악 | 신뢰하지 않는 중간 노드다. 키가 없고 종단 간 암호화이므로 터널 내용·키는 노출되지 않는다. 노출되는 것은 "누가 누구에게 연결하는가"라는 메타데이터와 가용성이다 |

### 8.2 Flow 모델 확장 (F-1 ~ F-3)

F-1 v1(D-041)에서 아래 첫 두 행, F-3 v1(D-042)에서 셋째 행(Trace 비밀 유출)이 **구현·테스트 완료**다(`docs/Machine_JSON_Schema_v1.md` §2, §4, `core/include/pf/trace.h`).

| 위협 | 대응(안) |
|---|---|
| 악성/잘못된 State Machine으로 무한 재시도·livelock(DoS) | Validator가 실행 전 거부: `NoExit`, `ImmediateCycle`, `UnboundedRetry`, `WaitWithoutTimeout`. 런타임은 이벤트 큐 상한과 타이머 범위를 강제 |
| 위조 패킷으로 상태 전이 유도 | 핸들러 Flow가 `Dropped`이면 **전이하지 않는다**(D-019 계약을 상태 층으로 확장) |
| Trace를 통한 비밀 유출 | 페이로드·키·평문·자격증명은 기록하지 않는 것이 기본이고, 테스트로 고정(알려진 테스트 키·평문 패턴 검색 0건). 바이트 덤프는 테스트 빌드 전용 sink만 |
| Trace·Machine 메타데이터를 통한 프롬프트 인젝션(PM-7에서 AI가 읽을 때) | trace의 문자열 필드는 데이터로만 취급. PM-7 위협 모델(MCP 계획)에서 상세화 |

### 8.3 OpenVPN 호환 서버 (PM-11, D-044)

`docs/PM11_OpenVPN_Server_Scope.md` §4: 인증 전 자원 소모(tls-crypt 검증 실패 패킷은 상태를 만들지 않음, 세션·IP별·속도 한도), 주소가 바뀐 클라이언트는 인증된 패킷으로만 갱신, 클라이언트 소스 주소 위조 거부, 서버 키는 KeyRef로만, 세션 끝나면 키 와이프.

V1(D-048)에서 정한 것:
- **인증 전에는 데이터 키가 없다**: 데이터 키는 인증 결정이 수락된 뒤에만 KeyStore에 들어간다. 거부·hand-window 초과·close는 모든 키를 와이프한다.
- **비밀번호**: `SecretString`으로만 다루고(복사 불가, 출력 불가, 소멸·이동 시 와이프), 수신 버퍼도 와이프한다. 클라이언트에게는 일반 문구 `AUTH_FAILED`만 보낸다(거부 사유는 서버 기록에만). 제어 문자가 든 사용자 이름·비밀번호는 훅에 넘기기 전에 거부한다.
- **재협상 신원 고정**: 같은 인증서 지문과 같은 사용자 이름이 아니면 세션을 닫는다. CRL은 재협상 때마다 TLS가 다시 검사한다. 만료된 CRL은 모든 클라이언트를 거부한다(닫힌 쪽으로 실패).
- **공유 tls-crypt 키의 한계**: 모든 클라이언트가 같은 tls-crypt 키를 가지므로, 키를 가진 클라이언트는 다른 세션의 패킷을 만들 수 있다. 다른 세션의 패킷이 이 세션의 재생 창을 움직이지 못하게 했지만(바인딩 뒤에만 commit), 평문 헤더에 보이는 **이 세션의 session id**를 쓴 미래 시각 패킷은 제어 채널을 방해할 수 있다. TLS가 내용을 보호하므로 세션 탈취는 아니고 가용성 문제다. 해법은 클라이언트별 키(tls-crypt-v2)이며 후속 과제로 둔다.
- **키 전환 불일치**: 한쪽만 새 키로 바뀐 반쯤 깨진 세션을 남기지 않는다. 확인할 수 없으면 세션을 닫고, 클라이언트가 다시 연결한다.
